# Design

## Context

Мотивация и границы — [proposal](proposal.md), поведение — [postgresql-storage](specs/postgresql-storage/spec.md). Статус: **предложено для просмотра; реализация не разрешена этим планом**.

Исследован `main` после PR №4. Корневой `pom.xml` содержит два модуля с Spring Boot; `backend/pom.xml` — MVC/Actuator, `worker/pom.xml` — non-web starter. Datasource и миграций нет. `BackendHttpTest` поднимает HTTP-контекст, `WorkerContextTest` — полный контекст без внешних сервисов. `WorkerApplication.main` закрывает контекст и печатает `WORKER_BOOTSTRAP_OK`; это конечный bootstrap, не живущий consumer.

`tools/process-smoke.mjs` и `frontend/e2e/connection.spec.mjs` запускают настоящие JAR. В CI есть Windows/Linux build-unit и Linux process-http; все пока без БД. Их положительные ветви нельзя оставить без datasource после изменения штатного старта. Версии toolchain и правила BOM — [technology-baseline.md](../../../docs/technology-baseline.md). Домен, версии, права и научные данные сохраняют границы [архитектуры](../../../docs/architecture.md).

## Goals / Non-Goals

**Goals:** единый путь миграций для обоих процессов; обязательное подключение на штатном старте; тестируемый отказ; обязательная PostgreSQL-интеграция Linux CI при независимой локальной сборке Windows.

**Non-Goals:** реализация предметного хранения и обмена заданиями; изменение finite-bootstrap жизненного цикла worker; схема HCh/Unitherm; новая научная модель. PostgreSQL-каркас не закрывает Q-DOM-001, Q-ACCESS-001, Q-ASYNC-001 и Q-RUN-001 из [реестра](../../../docs/open-questions.md).

## Decisions

### D-01 — Один ресурсный модуль миграций

Предлагается добавить `storage-migrations` в Maven reactor: обычный JAR только с `src/main/resources/db/changelog/`, без Java-домена, DTO, репозиториев и общих Spring-компонентов. Backend и worker зависят от одной версии этого модуля, используют JDBC datasource и Liquibase integration Spring Boot. При реализации проверить точные starter coordinates, управляемые BOM версии JDBC/Liquibase и лицензии; базовый Spring Boot не обновлять ради этой задачи.

Один master XML-changelog включает неизменяемые упорядоченные changeset с постоянными путями/id/author. Первый changeset выполняет технический PostgreSQL `SELECT 1`; его выполнение фиксируется Liquibase. Продуктовых таблиц пока нет: только служебные `DATABASECHANGELOG`/`DATABASECHANGELOGLOCK`. Это позволяет проверить реальное применение, checksum и идемпотентность без преждевременной доменной схемы. Контроль наличия прикладных данных выполняется тестом в отдельной технической таблице, не поставляемой приложению.

Liquibase — единственный прикладной механизм миграций: без Flyway, `schema.sql`/`data.sql` и Hibernate DDL. JPA пока не добавлять; при будущей JPA-интеграции запретить автоматическую генерацию схемы. Исторический changeset не редактировать и не включать `runAlways`/`runOnChange` для маскировки изменений.

Альтернативы: копирование changelog в оба модуля создаёт две расходящиеся истории; миграции только в backend требуют отдельного порядка запуска и проверки версии для worker; отдельный migrator добавляет третий процесс. Общий ресурсный JAR оставляет два существующих процесса и один источник миграций.

### D-02 — Оба процесса мигрируют до успешного старта

Оба приложения применяют один changelog на одной БД/схеме. Liquibase сериализует обновления своей блокировкой. Для этого этапа используются внешне заданные credentials роли с правами миграции; раздельные migrator/runtime-роли и rolling upgrade разных версий — будущий эксплуатационный дизайн, а не готовая гарантия.

Успешный bootstrap/readiness возможен после миграции. Worker сохраняет конечный lifecycle и после закрытия контекста сообщает, что PostgreSQL-проверка выполнена, а обработка заданий не реализована. Backend сохраняет loopback bind и прежние ограничения HTTP; liveness остаётся показателем живого процесса, отдельная проверка БД подтверждает интеграцию. Ошибка подключения или миграции проходит наружу без catch-and-continue.

Конкурентный чистый старт обоих JAR обязателен в CI: проверить также создание служебных таблиц на пустой БД, а не только блокировку готовой истории. Если выявится гонка конкретной версии Liquibase, устранить её в пределах согласованного старта и повторить сценарий; не считать наличие механизма блокировки доказательством прохождения теста.

Альтернатива — ленивый datasource с успешным стартом до первого обращения — не выполняет критерий явного отказа. Бесконечный retry и автоматический сброс lock/checksum исключены.

### D-03 — Внешние настройки и конечные ожидания

Обязательные настройки обоих процессов: `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD` либо эквивалентные Spring properties из внешнего защищённого файла. Пароль не передавать в CLI и не включать в JDBC URL; URL с user/password отклонять до инициализации драйвера. Без рабочих defaults. Общее имя changelog, PostgreSQL driver и технические таймауты допустимы в поставляемой конфигурации.

Предлагаемые пределы: connect/login/socket timeout драйвера до 10 секунд, получение соединения пула до 10 секунд, ожидание Liquibase lock до 1 минуты с коротким polling. Конкретные свойства проверить на BOM-версии; финальные значения и единицы документировать. Негативные process-тесты ограничены 60 секундами для подключения/миграции и 120 для занятого lock. В CI предусмотрен больший общий job timeout для всех отдельных сценариев.

Неполная конфигурация проверяется до попытки подключения. Штатный запуск с отключённым Liquibase не предлагается как путь обхода обязательной инициализации. Проверить, что настройки приложения не допускают успешный старт без требуемой миграции. У тестового отключения автоконфигурации D-04 нет поставляемого профиля.

Журналы не выводят datasource properties/URL с credentials/пароли. Негативный тест передаёт уникальный учебный пароль и проверяет его отсутствие в собранных stdout/stderr. Логи сохраняются с фильтрацией; безопасные примеры используют имена-заполнители, а CI — только временные credentials изолированного сервиса. Реальные адреса и секреты не нужны.

Область отказа здесь — **инициализация**: потеря соединения до завершения старта обязана дать ошибку. Поведение при обрыве после успешного старта, восстановление заданий и доставка остаются за рамками №6; изменение не обещает прекращение работающего backend при каждом сетевом сбое.

### D-04 — Разделение обычных тестов и PostgreSQL-интеграции

Обычный `mvnw verify` на Windows/Linux проверяет сборку, изолированный HTTP/lifecycle и валидацию конфигурации без внешних сервисов. Тесты HTTP/lifecycle, не проверяющие storage, явно отключают только datasource/Liquibase autoconfiguration в `src/test` и называются изолированными. Это не embedded PostgreSQL, H2 или доказательство подключения. Тестовые overrides не попадают в JAR.

Реальные PostgreSQL-тесты запускаются отдельным Maven-профилем `postgresql-it` через Failsafe в фазах integration-test/verify. Профиль активируется явно; отсутствие обязательных настроек, БД или тестов завершает его ошибкой. Он строит оба JAR и проверяет их штатные entrypoint, не подменяя запуск mock-контекстом. Альтернатива Testcontainers допустима технологически, но service container CI уже даёт нужную изоляцию без зависимости тестов от Docker API. Здесь выбран service container и обычный JDBC.

Тестовый harness получает только параметры выделенной CI-БД, выдаёт каждому сценарию отдельную БД либо схему с одинаковой настройкой JDBC/Liquibase у обоих приложений. Он создаёт техническую probe-таблицу **только тестовыми средствами**, записывает строку после миграции и читает её через новое соединение после остановки и повторного старта приложений. Прикладной changelog таблицу не содержит. Тест не выдаёт это за сохранение модели через REST и не доказывает переживание потери диска.

Для ошибочного changeset использовать отдельный test-only changelog; checksum-сценарий меняет только тестовую копию/изолированную историю. Для lock-сценария harness удерживает реальную блокировку на тестовой БД. Ни один негативный тест не портит штатный ресурс миграций или пользовательскую БД. Все дочерние процессы, соединения и тестовые схемы закрываются в finally.

### D-05 — CI и существующие process/HTTP/E2E

| Проверка | Среда и ожидаемое изменение |
| --- | --- |
| Build-unit | Windows Server 2022 и Ubuntu 24.04: сборка и изолированные тесты без БД/Docker; контрактные и frontend-проверки сохраняются |
| PostgreSQL integration | Отдельный обязательный job Ubuntu 24.04 с `postgres` service container и readiness check; Maven-профиль выполняет SCN-STORE-001–009 |
| Process/HTTP/browser | Linux job получает собственную PostgreSQL; `tools/process-smoke.mjs` и дочерние backend-процессы E2E получают её настройки; SCN-STORE-011 и прежние проверки HTTP/портов/изоляции frontend |
| Windows PostgreSQL run | Только при явно предоставленной доступной БД; установка/подключение к VPS этим планом не требуется. Локальный итог интеграции честно `NOT_RUN` |

При реализации выбрать поддерживаемый стабильный PostgreSQL, проверить совместимость выбранных JDBC/Liquibase и закрепить образ по версии/digest в workflow и источники в технологической основе. Не использовать `latest`. Service readiness — предпосылка, не итог миграционных тестов; не разрешать `continue-on-error`, условный пропуск и успешное завершение при отсутствии сервиса.

Process smoke больше не печатает общий `PostgreSQL/Kafka NOT_CONFIGURED`: PostgreSQL получает свой проверенный результат, Kafka остаётся `NOT_IMPLEMENTED / NOT_RUN`. E2E передаёт datasource только в окружение JVM, не в браузерный bundle и не в `VITE_*`. Существующие инварианты адресов frontend/backend и негативный прогон с отличающимися environment/`.env.local` сохраняются. Переписывать UI не требуется.

### D-06 — Документация и трассировка

README/docs/development обновляются только после реализации проверенными командами Windows и Linux; объясняются переменные, требование доступной PostgreSQL для запуска, отдельный интеграционный профиль и ограниченность bootstrap worker. Точные JDBC/SQL-команды зависят от реализованного harness, сейчас не выдаются как существующие.

Отчёт связывает SCN-STORE с результатом и CI run; отдельно помечает сборку, запуск, HTTP, availability и storage integration. Отсутствие предметных таблиц означает, что сохранность проектов/моделей/прав/расчётов всё ещё не реализована. ADR-0006 и PROP-DATA-001 не переводятся в «Принято» этим техническим изменением.

### Официальные основания технического подхода

Проверены 26 октября 2026 года: [Spring Boot database initialization](https://docs.spring.io/spring-boot/how-to/data-initialization.html) описывает автоматический Liquibase на старте, общий datasource, настройку master changelog и использование одного механизма инициализации. Это основание подхода; точные artifacts/properties сверяются с закреплённой версией при реализации.

[Разбор параллельных миграций Liquibase](https://support.liquibase.com/hc/en-us/articles/29383026247579-How-to-handle-long-running-queries-on-a-single-database) подтверждает назначение общей истории и блокировки. Точный параметр ограничения ожидания проверить по используемой версии. [GitHub Actions PostgreSQL services](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers) описывает PostgreSQL-сервис на Linux runner. Эти источники не подтверждают совместимость ещё не выбранных версий или выполненный CI проекта.

## Risks / Trade-offs

- Обязательная БД ломает старый запуск без сервисов → обновить все JAR-launchers, тесты и инструкции одной реализацией; основной Windows build оставить изолированным.
- Оба процесса имеют миграционные права → приемлемый технический каркас для изолированной разработки/CI; эксплуатационные роли и обновления разных версий проектировать отдельно до deployment.
- Liquibase может оставить lock после аварии → отказ с конечным ожиданием, без автоматического снятия чужого lock; восстановление требует отдельной диагностированной эксплуатационной процедуры.
- Нейтральный baseline не хранит предметные объекты → отчёт ограничен реальной технической проверкой; последующие story добавляют таблицы и предметную приёмку.
- Service container требует Docker у Linux runner → GitHub-hosted Ubuntu; на Windows Docker/WSL2 не становятся обязательными. Отсутствие подходящей Linux-среды блокирует интеграционную приёмку.

## Migration Plan

1. Представить этот план; до нового поручения не менять зависимости, runtime или workflow. Существующие статусы вычислительного контракта и старые delta specs сохраняются.
2. После разрешения реализации актуализировать AGENTS/OpenSpec context и границы этапа, не снимая запретов на решатель, Kafka, UI и VPS; выполнить [tasks](tasks.md).
3. В чистой CI-БД проверить baseline, повторный/конкурентный старт, probe и отказы. Существующая пользовательская БД не мигрируется автоматически в рамках работы агента.
4. Runtime-обновление представляется отдельным PR. При откате приложения baseline и история Liquibase сохраняются; автоматического drop или разрушительного rollback нет. На этом шаге прикладных таблиц нет, будущие доменные миграции требуют собственного плана совместимости.
5. Merge и archive/sync существующих изменений не выполнять. Новое изменение не архивировать как реализованное по факту готовности документов.

## Open Questions

Блокирующих предметных решений для технического каркаса нет. Проверка конкретных dependency coordinates, лицензий, PostgreSQL image/digest и имён timeout properties — ограниченная техническая задача перед установкой (REQ-TECH-002), не повторный выбор стека. VPS, схема предметных данных и жизненный цикл заданий остаются за рамками изменения.
