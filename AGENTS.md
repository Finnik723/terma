# Инструкции агенту

- Отвечай по-русски, если пользователь не попросил другой язык. Пользователь — системный аналитик и архитектор, научный эксперт проекта — его отец. Рутинную техническую работу выполняй самостоятельно в пределах разрешённого этапа.
- Сначала прочитай существующие инструкции, осмотри файлы и проверь `git status`, если каталог является Git-репозиторием. Анализируй пользовательские изменения перед редактированием; не перезаписывай их без разбора.
- Все дальнейшие изменения готовь в отдельной ветке и представляй через pull request в `main`. Не отправляй изменения напрямую в `main` и не переписывай опубликованную историю без явного поручения пользователя на такое исключение.
- Источник требований, сценариев и предложений — [docs/project-foundation.md](docs/project-foundation.md). Термины — [словарь](docs/domain-glossary.md), ответственность модулей — [архитектура](docs/architecture.md), решения и их статусы — [ADR](docs/adr/README.md), неопределённости — [открытые вопросы](docs/open-questions.md).
- Сохраняй идентификаторы `REQ-*`, `SCN-*`, `PROP-*`, `DEMO-*`, `Q-*` и номера ADR. Новым положениям давай новые идентификаторы; не используй старые для другого смысла. Ссылками связывай документы вместо расходящихся копий требований.
- Разделяй согласованные требования, технические предложения и открытые вопросы. Не повышай статус предложения без решения пользователя. При изменении статуса обновляй связанные документы и основания решения.
- До реализации функционального изменения следуй [процессу SDD](docs/development-workflow.md): требования и проверяемые сценарии, дизайн, задачи, просмотр пользователем, реализация и проверки, затем актуализация спецификаций и архивирование по правилам используемой версии OpenSpec. Не выдумывай команды или служебные каталоги OpenSpec.
- OpenSpec описывает поведение, OpenAPI — HTTP-контракт, ADR — архитектурные решения. При появлении спецификаций укажи их как источник подробного поведения в документации и сохраняй трассировку исходных идентификаторов.
- OpenSpec 1.15.0 инициализирован для Codex; контекст — [openspec/config.yaml](openspec/config.yaml). [Application-scaffold](openspec/changes/application-scaffold/proposal.md) уже реализован, собран и проверен, PR №2 объединён; версии закреплены в [технологической основе](docs/technology-baseline.md) и manifests/lockfile. Его архивирование — отдельное действие, не часть текущего задания. Основной каталог спецификаций пока пуст; готовность артефактов и схем не означает выполнения будущего поведения.
- Для будущего расчётного прототипа требуется реальная упрощённая минимизация и раздельные вход/выход (REQ-SCI-008–REQ-SCI-012, ADR-0010); возврат входа без расчёта отменён. Метод, постановку, данные и контрольные примеры согласовать с научным экспертом до реализации (Q-SCI-004–Q-SCI-006). Не приписывай упрощённой модели доказанное равновесие реальной системы или невычисленные свойства. Не выдумывай HCh API, структуру Unitherm и доказанную совместимость; подтверждённые внешние сведения сопровождай источниками, проектные допущения помечай явно.
- Учитывай права, неизменяемые версии, конфликты и воспроизводимость с начала доменного проектирования. Серии и перенос оркестрирует worker; решатель получает одну задачу реактора.
- Для разработки учитывай Windows 10, IntelliJ IDEA Community и отсутствие обязательного WSL2. Давай полные команды с известными путями и Windows-вариантами, включая `mvnw.cmd`, когда такие файлы действительно появятся. Перед установкой проверяй актуальную совместимость и бесплатную доступность зависимостей; preview по умолчанию не выбирай.
- Обновляя документы, проверяй относительные ссылки, статусы, трассировку, отсутствие противоречий и неподтверждённых научных утверждений. Не сохраняй секреты, закрытые материалы или вымышленные команды запуска.
- Текущий этап — документационный [контракт Terma v1](docs/solver-contract.md), [ADR-0011](docs/adr/0011-equilibrium-contract-and-hch-adapter.md), схемы/синтетические примеры и [equilibrium-engine-contract](openspec/changes/equilibrium-engine-contract/proposal.md), REQ-STAGE-005. Это логический контракт приложения, не программный API HCh. Реализацию решателя/адаптера, установку оптимизатора, вычислительный модуль, Java DTO, PostgreSQL/Kafka и изменение UI не выполнять. Проверять схемы готовым валидатором разрешено; LP/постоянные H/S/V/Hipparchus остаются кандидатом без выбора версии или зависимости.
- По ревью PR №4 от 26 октября разрешены сохранённый сценарий проверки контракта в tools, его изолированные закреплённые зависимости и запуск в Windows/Linux CI. Это инструменты проверки документов/фикстур, не код решателя. Требования свойств имеют code/scope с семантикой всех присутствующих объектов; версия capabilities отделена от версий calculate. Подробности — в едином контракте, без повторного выбора научной методики.
- Архитектурные и научные решения обсуждаются пользователем в web; локальный Codex документирует согласованное и реализует конкретно порученные задачи. При пробеле, меняющем предметный контракт, описывай проблему и варианты пользователю, не выбирай новую научную модель самостоятельно. Обычные технические решения реализации остаются в компетенции локального Codex. Не возобновляй выбор методики в текущем контрактном задании.
- Сохраняй серверные права, неизменяемые версии моделей/библиотек и фиксации запусков, историю результатов, воспроизводимость и будущий CSV. Адаптер изолирует неизвестный API/runtime/данные HCh; неизменность контракта — цель, не гарантия, несовместимые изменения требуют нового major и сохранения чтения старых результатов. Не развёртывай инфраструктуру, не подключайся к VPS, не запрашивай секреты. Разрешены commit/push документации и PR в main; merge, archive/sync каркаса и реализация решателя в этом задании запрещены.
