# Технические требования реализованного каркаса

Основания — [основа проекта](project-foundation.md) и [ADR-0009](adr/0009-application-scaffold.md). Ниже сохранены критерии сборки, запуска и окружения с прежними идентификаторами. Фактические результаты — в [отчёте проверки](verification.md), команды — в [development.md](development.md). Это описание реализованного каркаса без БД и заданий; последующие задачи могут менять его поведение.

Задача №6 уже меняет штатный запуск: backend/worker требуют настроенную PostgreSQL по [REQ-STORE и SCN-STORE](storage-foundation.md). Прежние SCN-BOOT/ENVCHK ниже описывают исходную приёмку каркаса, а не текущую гарантию старта JAR без БД. Обычная сборка и изолированные тесты по-прежнему работают без внешних сервисов.


## Сборка


### REQ-BUILD-001 — Раздельные артефакты одного репозитория

Репозиторий должен позволять собрать отдельные исполняемые артефакты backend и worker и отдельный frontend. Сборка одного приложения не должна требовать запущенного другого приложения.

#### SCN-BUILD-001 — Сборка без работающих процессов

- **Когда** разработчик собирает каркас с корректным toolchain и доступом к репозиториям зависимостей, но без запущенных frontend, backend и worker
- **Ожидается** получены два независимо запускаемых JVM-артефакта и статический frontend; результат обозначен как успешная сборка, без заявления о запуске системы

### REQ-BUILD-002 — Закреплённые инструменты и зависимости

Каркас должен содержать закреплённые версии инструментов сборки, Windows/Unix wrapper для JVM и lockfile frontend. Стандартная повторная установка должна использовать зафиксированное разрешение зависимостей без изменения lockfile.

#### SCN-BUILD-002 — Повторная установка из чистого checkout

- **Когда** два чистых checkout одного коммита проверяются на выбранных версиях инструментов с доступом к источникам зависимостей
- **Ожидается** используется одинаковая версия сборщика JVM и одинаковое разрешение frontend-зависимостей, а manifest и lockfile остаются неизменными

#### SCN-BUILD-003 — Несогласованные manifest и lockfile

- **Когда** manifest frontend изменён без соответствующего обновления lockfile и запускается стандартная повторная установка
- **Ожидается** установка завершается ошибкой; lockfile не переписывается ради успешной проверки

### REQ-BUILD-003 — Обычные проверки Windows без инфраструктуры

Сборки и обычные unit/компонентные тесты должны выполняться на Windows 10 без WSL2, Docker Engine, PostgreSQL, Kafka и доступа к пользовательскому VPS. Первая загрузка инструментов и зависимостей может требовать сети.

#### SCN-BUILD-004 — Локальные проверки без Docker и VPS

- **Когда** на Windows 10 доступны выбранные JDK и Node/npm, но отсутствуют WSL2, Docker, PostgreSQL, Kafka и соединение с VPS
- **Ожидается** сборки и обычные unit/компонентные тесты выполняются; пропуск инфраструктурных проверок не выдаётся за их успешное прохождение

### REQ-BUILD-004 — Границы будущего научного расширения

Каркас должен документировать отделение backend от worker и будущей расчётной подсистемы. Каркас не должен вводить научные контракты, фиктивные доменные API, задания или Kafka-сообщения для демонстрации сборочных границ.

#### SCN-BUILD-005 — Ревью границ

- **Когда** проверяются граф сборочных зависимостей и содержимое каркаса
- **Ожидается** backend и worker не зависят друг от друга, описано место будущего адаптера и научных данных, а доменные/научные типы, обработчики заданий и демонстрационные Kafka-сообщения отсутствуют


## Запуск и HTTP


### REQ-BOOT-001 — HTTP-проверка процесса backend

Backend должен запускаться без PostgreSQL/Kafka и предоставлять техническую HTTP-проверку своей жизнеспособности. Её положительный ответ должен означать только, что процесс отвечает; он не должен подтверждать доступность инфраструктуры или расчётной подсистемы.

#### SCN-BOOT-001 — Backend без инфраструктуры

- **Когда** запускается собранный backend с корректной локальной конфигурацией без PostgreSQL/Kafka
- **Ожидается** техническая проверка возвращает положительный HTTP-ответ; документация и UI не трактуют его как готовность БД, брокера или расчётов

### REQ-BOOT-002 — Отдельная проверка bootstrap worker

Worker должен иметь независимо запускаемую проверку bootstrap, завершающуюся кодом 0 после успешной инициализации и корректного закрытия контекста. Она не должна требовать PostgreSQL/Kafka, запускать научные задания или объявлять готовность потребителя сообщений.

#### SCN-BOOT-002 — Успешная инициализация worker

- **Когда** отдельным процессом запускается собранный worker в документированном режиме проверки bootstrap без внешней инфраструктуры
- **Ожидается** наблюдается признак успешной инициализации, процесс завершается кодом 0, научные задачи не выполняются, инфраструктура явно не проверена

#### SCN-BOOT-003 — Ошибка инициализации worker

- **Когда** проверка bootstrap не может завершить инициализацию из-за некорректной конфигурации
- **Ожидается** процесс завершается ненулевым кодом с понятной причиной и не выдаёт признак успешного bootstrap

### REQ-BOOT-003 — Экран честной технической проверки

Frontend должен показывать обозначение технического каркаса без доступных научных расчётов. Проверка backend должна использовать настоящий HTTP-ответ, отдельно показывать состояния ожидания, успеха и недоступности и не объявлять PostgreSQL/Kafka или worker проверенными.

#### SCN-BOOT-004 — Настоящая HTTP-связь

- **Когда** пользователь запускает проверку связи и backend возвращает ожидаемый положительный технический ответ
- **Ожидается** frontend показывает подтверждение ответа backend, а PostgreSQL/Kafka и worker остаются в явно обозначенном состоянии «не подключены / не проверены»

#### SCN-BOOT-005 — Ошибка или таймаут

- **Когда** backend остановлен, отвечает ошибкой, неожиданным содержимым или не отвечает в установленный срок
- **Ожидается** frontend показывает недоступность или ошибку проверки и не сохраняет прежний успешный результат как актуальный

### REQ-BOOT-004 — Ошибка запуска не маскируется сборкой

Конфликт локального порта или недопустимый технический параметр должен давать явную ошибку запуска соответствующего процесса. Успешная сборка не должна подменять результат проверки запуска.

#### SCN-BOOT-006 — Занятый порт

- **Когда** порт HTTP-процесса уже занят и запускается backend или frontend на этом порту
- **Ожидается** запуск сообщает об ошибке, а успешная сборка остаётся отдельным результатом; frontend не переключается молча на другой порт


## Окружение и проверки


### REQ-ENVCHK-001 — Явная техническая конфигурация

Технические параметры каркаса должны поддерживать документированное задание через окружение и безопасные локальные значения по умолчанию. Недопустимые значения должны приводить к понятной ошибке, без молчаливого подключения к альтернативной инфраструктуре.

#### SCN-ENVCHK-001 — Переопределение параметров

- **Когда** разработчик задаёт допустимый локальный порт backend и адрес его технической проверки через документированное окружение
- **Ожидается** процессы используют заданные значения, HTTP-проверка достигает выбранного backend, а примеры не содержат адресов пользовательского VPS

#### SCN-ENVCHK-002 — Недопустимый параметр

- **Когда** задан некорректный порт или недопустимое значение технического параметра
- **Ожидается** запуск или проверка явно завершается ошибкой; значения секретов не попадают в диагностику

### REQ-ENVCHK-002 — Безопасные примеры

Каркас должен содержать безопасные примеры только используемых технических параметров. Секреты не должны попадать в Git, frontend bundle или диагностический вывод. Примеры не должны содержать реальные адреса или выдуманные параметры пользовательского сервера.

#### SCN-ENVCHK-003 — Проверка примеров и bundle

- **Когда** проверяются отслеживаемые примеры конфигурации, Git-игнорирование локальных файлов и собранный frontend
- **Ожидается** примеры содержат только безопасные локальные параметры, локальные секреты не отслеживаются, а в клиентском коде нет паролей или серверных секретов

### REQ-ENVCHK-003 — Раздельные результаты проверок

Проверки должны различать сборку, запуск процесса, HTTP-связь, доступность инфраструктуры и интеграции. Невыполненная или не настроенная проверка не должна показываться как успешная; отсутствующая зависимость не должна подменяться другой БД или фиктивным брокером.

#### SCN-ENVCHK-004 — Инфраструктура отсутствует

- **Когда** сборки, bootstrap и HTTP-проверки успешны, но PostgreSQL/Kafka не настроены и их проверки не выполнялись
- **Ожидается** успешны только соответствующие технические категории; инфраструктура и её интеграции явно обозначены как не настроенные или не выполненные

#### SCN-ENVCHK-005 — Обязательный положительный HTTP-smoke недоступен

- **Когда** обязательная положительная HTTP-проверка каркаса запускается без доступного backend
- **Ожидается** проверка завершается ошибкой с указанием недоступного процесса, а не скрытым skip или фиктивным успешным ответом; отсутствие инфраструктуры не компенсируется H2 или фиктивным брокером

### REQ-ENVCHK-004 — CI без пользовательского VPS

CI каркаса должен выполнять сборки, обычные тесты, проверки bootstrap и настоящую HTTP-связь frontend/backend без пользовательского VPS и без инфраструктурных секретов. Ошибка обязательного шага должна делать соответствующую проверку CI неуспешной.

#### SCN-ENVCHK-006 — Чистая CI-среда

- **Когда** CI запускается для отдельной ветки или PR без доступа к пользовательскому VPS и его секретам
- **Ожидается** технические проверки выполняются на выбранных средах, результаты разделены по категориям, а непредусмотренные каркасом PostgreSQL/Kafka-интеграции не объявляются пройденными

### REQ-ENVCHK-005 — Windows-документация соответствует реализации

Документация каркаса должна содержать проверенные полные Windows-команды сборки, обычных тестов, запуска и HTTP-проверки, с предварительными условиями и смыслом результата. Будущие команды не должны представляться работающими до появления соответствующих файлов.

#### SCN-ENVCHK-007 — Проход инструкции

- **Когда** разработчик выполняет документированный путь из чистого checkout реализованного каркаса на Windows с выбранным toolchain
- **Ожидается** все упомянутые файлы и команды существуют, WSL2/Docker не требуются, а инструкция не обещает научных расчётов или инфраструктурной готовности

### REQ-ENVCHK-006 — План инфраструктуры без развёртывания

Первое изменение должно содержать только план PostgreSQL/Kafka на Ubuntu VPS: необходимые сведения, защищённый доступ и будущие проверки. Оно не должно включать развёртывание, обращения к VPS, публичное открытие БД/брокера или конфигурацию с догадками о сервере.

#### SCN-ENVCHK-008 — Проверка границ плана

- **Когда** проверяется инфраструктурная часть изменения
- **Ожидается** перечислены сведения и решения для отдельного инфраструктурного изменения, нет реальных адресов, секретов, выдуманных ресурсов/портов сервера или выполненных удалённых действий
