# Design

## Context

Мотивация/объём — [proposal](proposal.md), поведение — [delta spec](specs/equilibrium-engine-contract/spec.md). Application-scaffold реализован, его версии закреплены и сборки/проверки выполнены. Этот дизайн оформляет только документы, схемы и примеры по архитектурному решению пользователя; не добавляет сборочный модуль или runtime. Фактические проверки каркаса — [отчёт](../../../docs/verification.md), версии — [технологическая основа](../../../docs/technology-baseline.md).

## Goals / Non-Goals

**Goals:** единый подробный контракт, машинно проверяемая форма, явная граница ядра/приложения, воспроизводимые документальные проверки и прослеживаемость принятых решений.

**Non-Goals:** научный выбор, численная реализация, Java DTO, новый HTTP/COM API, инфраструктура и изменение UI. Выполненные документальные задачи не подтверждают будущее вычисление. Архивирование каркаса и main-spec sync исключены.

## Decisions

### D-C01. Единый источник и слой адаптации

[solver-contract.md](../../../docs/solver-contract.md) содержит подробную семантику; ADR — основания, delta spec — проверяемые обязательства, foundation — обзор с ID и ссылками. JSON Schema описывают структуру, а не повторяют внутреннюю научную модель. Дублирование полного контракта во всех обзорах отклонено из-за риска расхождения.

Логический EquilibriumEngine — граница приложения, а не интерфейс HCh. После получения исходников допустимы иной runtime/процесс, внутренний API и связанные данные за адаптером. Ни обязательный callback g(T,P), ни отдельный HTTP-сервис не вводятся. Контекст/права/история запуска остаются в приложении.

### D-C02. JSON Schema 2020-12 и локальные ссылки

Схемы находятся в [contracts/equilibrium/v1](../../../contracts/equilibrium/v1/README.md): common, request, result, capabilities, chemical-system. Локальный registry регистрирует URN `$id`, валидатор не получает зависимости через сеть. Строгие объекты 1.0 обнаруживают случайные поля оптимизатора/COM; расширяемые значения phaseType и namespaced properties заданы явно. Отдельные схемы будущих minor/major версий не заменяют старые файлы.

Элементный запрос и фазовый выход не объединяются в DTO «состояние на входе/выходе». Начальное распределение для теста минимизации остаётся отдельной фикстурой. Для распознанного INVALID_INPUT результат может не иметь извлечённых условий или использованных ссылок (null с диагностикой); успех обязан иметь полный разрешённый provenance и условия. Нечитаемый конверт отклоняется до логического calculate без вымышленных идентификаторов.

### D-C03. Два уровня проверки

Готовый валидатор проверяет метасхемы, `$ref`, положительные примеры и ожидаемый отказ отрицательных. Отдельная арифметическая проверка примеров сопоставляет вход → итог → сумму фаз → стехиометрию species, нейтральность, уникальность/ссылки и однородный перенос. Это обработка фикстур, не оптимизация. Граница JSON Schema явно перечислена в подробном контракте; не заменяем вычислительную приёмку формой документа.

Все примеры синтетические и составлены вручную. Пример смеси с двумя экземплярами GAS демонстрирует вместимость формата, а capabilities pure-phase не обещают её поддержки. Дополнительные свойства опущены; отдельно проверяются мутации свойств с единицами/отсчётом энергии. Результат CONVERGED в примере — гипотетический конверт, не запуск ядра.

### D-C04. История и возможности

Сохранение интерфейса при HCh — цель с явным major-переходом при предметной необходимости. Отсутствие возможностей/данных не вызывает скрытый fallback; внутренние коды и единицы преобразует адаптер. Опубликованные версии моделей/библиотек, зафиксированный вход и конечные результаты остаются неизменяемыми; повторный расчёт создаёт новый provenance. Общие solverOptions не становятся каналом произвольных параметров ядра.

### D-C05. Статусы проекта

Обзоры и инструкции указывают фактически выполненную реализацию application-scaffold и текущий документационный этап. Его 17 выполненных задач и критерии не меняются. Старое обещание «сначала определить всё научное, затем любой контракт» уточняется: пользователь уже закрепил внешний v1, неизвестное внутреннего ядра не блокирует этот PR. [Кандидат](../../../docs/solver-contract.md) LP/H/S/V/Hipparchus сохраняется кратко как PROP-SOLVER-001, без версии/зависимости.

## Risks / Trade-offs

- [Неизвестный HCh может потребовать изменения контракта] → версия, исторические readers и явное решение пользователя вместо обещания совместимости.
- [Схема может выглядеть как выполненный решатель] → явные статусы документационного этапа, синтетические примеры, вычислительные сценарии остаются будущими.
- [Некорректный баланс проходит структурную схему] → обязательная семантическая проверка и демонстрация этого ограничения в отчёте.
- [Фазовые определения могут расходиться с выходом] → проверка IDs, модели, принадлежности и стехиометрии по выбранной версии системы.
- [Публикации неполны] → источники/степень доступа отделены от наших выводов; внутренние методы, файлы и структуры HCh не выдумываются.

## Migration Plan

Изменяются только документы/схемы. Откат — обратный документационный PR; БД и исторические результаты отсутствуют и не мигрируются. После ревью этого контракта научная реализация требует отдельного поручения/изменения. Не архивировать application-scaffold и не синхронизировать контракт в main specs как выполненную функцию в этом задании.

## Open Questions

Для документального комплекта блокирующих неизвестных нет. Q-HCH-001 и остатки Q-SCI-001/002 относятся к поставке HCh; Q-SCI-004–006 — к конкретной временной реализации/данным/численной приёмке. Они не меняют текущий объём задач и не требуют повторного выбора методики здесь. При будущем предметном противоречии контракту вопрос возвращается пользователю с вариантами.
