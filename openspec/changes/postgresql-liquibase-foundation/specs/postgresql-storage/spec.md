# Spec Delta

## Purpose

Обеспечить проверяемую основу PostgreSQL-хранения для backend и worker: конфигурацию, миграции и явные ошибки старта до добавления предметных таблиц. Это планируемое поведение задачи №6, не утверждение о реализованном сохранении проектов или расчётов.

Трассировка: REQ-STORE-001–006, REQ-TECH-001–002, REQ-ENV-001–003 и REQ-PROC-001 в [основе проекта](../../../../../docs/project-foundation.md); [ADR-0005](../../../../../docs/adr/0005-selected-stack-and-async-boundary.md). Дополнительные технические сценарии раскрывают критерии №6 и предложены для ревью; ADR-0006 этим не принимается.

## ADDED Requirements

### Requirement: REQ-STORE-001 — Внешняя конфигурация подключения

Backend и worker SHALL получать JDBC URL, имя пользователя и пароль PostgreSQL только через внешнюю конфигурацию/окружение, без рабочих значений по умолчанию. Секреты и реальные адреса SHALL отсутствовать в репозитории; диагностический вывод SHALL исключать секреты. Примеры содержат только явно учебные значения.

#### Scenario: SCN-STORE-001 — Оба приложения используют заданную БД
- **WHEN** каждое приложение запускается с внешними настройками доступной тестовой PostgreSQL
- **THEN** подключение и миграции используют указанную БД; JDBC-запрос подтверждает PostgreSQL, а не встроенную замену
- **AND** смена тестовой БД через конфигурацию не требует пересборки JAR

#### Scenario: SCN-STORE-002 — Неполная конфигурация
- **WHEN** у любого приложения отсутствует обязательная настройка URL, пользователя или пароля
- **THEN** старт завершается с ненулевым кодом в ограниченное время, без обращения к неявному localhost или встроенной БД
- **AND** диагностика называет ошибку конфигурации, не раскрывая заданный пароль

### Requirement: REQ-STORE-002 — Единые миграции

Liquibase SHALL быть единственным механизмом прикладных миграций для обоих приложений. Чистая БД SHALL получать одну согласованную историю changeset; повторный старт SHALL сохранять историю и данные, не применяя выполненные changeset повторно. Предметные таблицы в это изменение не входят.

#### Scenario: SCN-STORE-003 — Чистая БД и последовательный повторный старт
- **WHEN** backend запускается на чистой PostgreSQL, затем останавливается, запускается worker и повторно запускается backend
- **THEN** базовый changeset отмечен выполненным ровно один раз с неизменным checksum, история и служебные таблицы Liquibase доступны обоим приложениям
- **AND** тестовая техническая запись сохраняется между стартами; таблицы проектов, моделей, прав и расчётов не создаются

#### Scenario: SCN-STORE-004 — Конкурентный запуск
- **WHEN** backend и worker одновременно запускаются с одной версией changelog на чистой тестовой БД
- **THEN** оба успешно заканчивают инициализацию в установленный срок, а каждый changeset записан ровно один раз
- **AND** ожидание блокировки миграций ограничено; успешный старт не предшествует завершению миграций

### Requirement: REQ-STORE-003 — Явный отказ старта

Каждое приложение MUST завершать старт с ненулевым кодом при недоступной PostgreSQL, отказе аутентификации или ошибке миграции. Ожидания подключения и блокировки SHALL иметь конечный предел. Отказ SHALL исключать успешный bootstrap/readiness и тихий fallback; диагностике достаточно причины без секретов.

#### Scenario: SCN-STORE-005 — Недоступная БД или неверный пароль
- **WHEN** любой из двух процессов запускается с недоступным endpoint, неверным тестовым паролем либо теряет соединение до завершения инициализации
- **THEN** процесс завершается с ненулевым кодом не позднее 60 секунд, без успешного bootstrap/readiness
- **AND** причина различима в журнале, пароль и credentials внутри JDBC URL не выводятся

#### Scenario: SCN-STORE-006 — Ошибка миграции или checksum
- **WHEN** любое приложение запускается с ошибочным тестовым changeset либо несоответствием checksum ранее выполненного changeset
- **THEN** процесс завершается с ненулевым кодом не позднее 60 секунд без успешного bootstrap/readiness
- **AND** ошибка не подавляется, история не очищается и checksum не пересчитывается автоматически ради успешного старта

#### Scenario: SCN-STORE-007 — Занятая блокировка миграции
- **WHEN** другое соединение удерживает блокировку дольше установленного лимита
- **THEN** ожидающее приложение завершает старт ошибкой не позднее 120 секунд, сохраняя блокировку владельца и историю

### Requirement: REQ-STORE-004 — Обязательная проверка настоящей PostgreSQL

Linux CI SHALL проверять на настоящей PostgreSQL подключение обоих приложений, миграции, повторный старт, техническое сохранение и негативные сценарии SCN-STORE-002, 005–007. Отсутствие БД или обязательной проверки MUST завершать проверку ошибкой; H2, mock, skip и один лишь TCP-check не заменяют интеграцию.

#### Scenario: SCN-STORE-008 — Полный PostgreSQL-прогон
- **WHEN** выполняется обязательная Linux CI-проверка хранения
- **THEN** она поднимает изолированную PostgreSQL, проверяет SCN-STORE-001–007 и отдельно сообщает результат интеграции
- **AND** остановленные тестовые процессы и временные данные очищаются без доступа к пользовательской БД

#### Scenario: SCN-STORE-009 — Сервис CI не поднялся
- **WHEN** PostgreSQL недоступна или проверка не может выполнить обязательный сценарий
- **THEN** job завершается ошибкой; успешная сборка, HTTP liveness и PostgreSQL availability не выдаются за пройденную интеграцию

### Requirement: REQ-STORE-005 — Windows без обязательного Docker

Сборка и изолированные тесты SHALL оставаться доступны на Windows 10 без Docker/WSL2 и БД. Их результат SHALL явно отличаться от PostgreSQL-интеграции. Штатный запуск приложения с БД и Linux process/HTTP/E2E SHALL использовать обязательное подключение, без поставляемого обходного режима без хранилища.

#### Scenario: SCN-STORE-010 — Изолированная локальная проверка
- **WHEN** выполняются обычные сборка и тесты на Windows без PostgreSQL
- **THEN** они не требуют Docker/WSL2, не поднимают встроенную БД и не пытаются подключиться к VPS
- **AND** отчёт обозначает PostgreSQL-интеграцию как не выполненную локально

#### Scenario: SCN-STORE-011 — Process и HTTP с PostgreSQL
- **WHEN** Linux CI запускает собранные JAR и существующие browser HTTP-проверки
- **THEN** приложения получают параметры изолированной PostgreSQL, миграции завершаются до успешного bootstrap/readiness, настоящий HTTP и изоляция frontend-конфигурации сохраняются
- **AND** результат не утверждает наличие Kafka, обработки заданий или научных вычислений

### Requirement: REQ-STORE-006 — Достоверная документация запуска

README и docs/development SHALL описывать реализованный способ конфигурации и проверки, безопасные примеры и ограничения среды. Отчёт SHALL отделять сборку, bootstrap, HTTP, доступность PostgreSQL и интеграцию. Отсутствующие предметные таблицы SHALL явно исключать заявление о сохранении проектов и расчётов.

#### Scenario: SCN-STORE-012 — Проверка инструкций и границ
- **WHEN** реализация представляется на ревью
- **THEN** документация содержит проверенные Windows-команды и Linux CI-путь, необходимые переменные и ожидаемые ошибки без реальных секретов/адресов
- **AND** фактические результаты имеют ссылки на проверки; недоступная локальная интеграция не отмечена пройденной, Kafka и предметное сохранение остаются будущей работой
