# Процесс разработки

## Источники истины

[Основа проекта](project-foundation.md) содержит исходные согласованные требования, сценарии и отдельно предложения. [Словарь](domain-glossary.md) задаёт термины, [архитектура](architecture.md) — обязанности, [ADR](adr/README.md) — решения с фактическими статусами, [открытые вопросы](open-questions.md) — ещё не решённые пункты и момент их закрытия.

OpenSpec 1.15.0 инициализирован для Codex. Контекст и правила подключены в [config.yaml](../openspec/config.yaml); первое изменение — [application-scaffold](../openspec/changes/application-scaffold/proposal.md). Подробное предлагаемое поведение находится в его delta specs с трассировкой `REQ-*`, `SCN-*` и ADR. Основной `openspec/specs/` пока пуст: будущее поведение не выдано за действующее. Этот комплект документов остаётся обзором исходных ограничений и целей; OpenAPI отвечает за будущий HTTP-контракт, ADR — за решения.

## Цикл функционального изменения

По `REQ-PROC-001`:

1. Описать цель, границы изменения, исключения и связь с исходными требованиями.
2. Зафиксировать поведение и проверяемые сценарии. Предложения сохранить предложениями до решения пользователя; новые допущения обозначить явно.
3. Подготовить технический дизайн и задачи; закрыть только те открытые вопросы, которые мешают именно этому изменению. Указать проверки и ограничения среды.
4. Дать пользователю просмотреть постановку, требования, дизайн и задачи. До этого не реализовывать функциональность.
5. Реализовать согласованный объём, проверить сценарии и необходимые технические свойства.
6. Актуализировать спецификации, обзорные документы, ADR и ссылки; архивировать изменение по правилам фактически используемой версии OpenSpec.

Проверки соотносятся с наблюдаемым поведением и риском. Документирование сценария не означает, что приложение уже существует или сценарий пройден.

## Ветки и pull request

По решению пользователя все дальнейшие изменения готовятся в отдельной ветке и представляются через pull request в `main`. Это относится и к документации. В PR указываются цель изменения, связанные требования и сценарии, выполненные проверки и существенные ограничения.

Прямое обновление `main` и переписывание опубликованной истории допускаются только по явному поручению пользователя на соответствующее исключение. Объединение двух первоначальных коммитов документации в один — такое отдельно порученное исключение; оно не меняет правило для последующей работы.

## Перенос контекста и публикация для ревью

Первоначальный перенос включал анализ каталога, инструкций и состояния Git, создание и актуализацию документации, проверки её согласованности и ссылок. Ограничения `REQ-STAGE-001` исключали код приложения, зависимости, конфигурации запуска, инфраструктуру, подключение к VPS, запросы секретов, commit/push и инициализацию OpenSpec. Документация была подготовлена и представлена пользователю.

Затем пользователь отдельно разрешил настроить Git и выполнить commit/push документации для ревью облачным агентом. Адрес репозитория и правила файлов находятся в [README](../README.md). Это поручение разрешает публикацию документации и служебных Git-файлов, сохраняя запрет на реализацию приложения, инициализацию OpenSpec и инфраструктурные действия до соответствующего следующего этапа.

Первый этап завершён. Его ограничения сохранены здесь как история; последующее поручение пользователя разрешило OpenSpec и подготовку первого изменения (`REQ-STAGE-002`). Действующий объём определяется следующим разделом.

## Подготовка первого изменения (история)

Фактически выполнена установка только OpenSpec 1.15.0 и штатная инициализация для Codex. Существующий AGENTS.md сохранён генератором. Созданы шесть skills в `.agents/skills/`, проектная конфигурация и изменение `application-scaffold`. Подробности инструмента и официальные источники — в [технологической основе](technology-baseline.md).

Были подготовлены [proposal](../openspec/changes/application-scaffold/proposal.md), три delta specs — [сборка](../openspec/changes/application-scaffold/specs/development-build/spec.md), [процессы/HTTP](../openspec/changes/application-scaffold/specs/technical-runtime/spec.md), [окружение/проверки](../openspec/changes/application-scaffold/specs/environment-verification/spec.md), [design](../openspec/changes/application-scaffold/design.md), [tasks](../openspec/changes/application-scaffold/tasks.md). PR №1 прошёл ревью и объединён пользователем.

Проверенные штатные команды для Windows из корня проекта:

```powershell
openspec.cmd --version
openspec.cmd status --change application-scaffold
openspec.cmd validate application-scaffold --strict --no-interactive
```

Подготовка выполнялась через `openspec-propose`. Затем пользователь явно разрешил реализацию. Значение `isPlanningComplete`/готовность артефактов означает только комплектность планирования, а не успешное выполнение задач.

## Текущий этап: реализация application-scaffold

Используется штатный `openspec-apply-change`: читать `instructions apply`, выполнять согласованные задачи, отмечать их только после реализации и проверки и повторно проверять прогресс. Разрешены необходимые зависимости, локальные/CI-проверки, commit/push отдельной ветки и PR. Согласованы дизайн и необходимый набор технологий каркаса, а не все предложенные ADR. Замена Temurin на 25.0.4.1+1 отдельно согласована из-за отсутствия Windows-дистрибутива 25.0.5+8.

Сохраняются исключения объёма из proposal. Запрещены VPS, доменные/научные функции и интеграции PostgreSQL/Kafka. Существенные замены технологий и критериев сначала согласуются; обычные исправления выполняются в рамках дизайна. Недоступная проверка явно остаётся невыполненной. Команды запуска — [development.md](development.md), результаты — [verification.md](verification.md).

До ревью реализации не выполнять archive/sync в основной каталог спецификаций и не делать merge PR самостоятельно. При последующем архивировании проверить как внутренние относительные ссылки перенесённых proposal/design/tasks/specs, так и ссылки на них из README, AGENTS.md и docs; одной проверки наличия архивной папки недостаточно.

### Где определён объём первого изменения

Границы, исключения и новые capability определены в proposal; структура, разделение Windows/Linux проверок, смысл запуска worker и план инфраструктуры — в design. Не следует дублировать их здесь. Реальное развёртывание на VPS явно исключено по поручению пользователя; расчётная подсистема, доменная функциональность, задания и CSV относятся к следующим изменениям. Наличие отдельных процессов не утверждает внутренние научные контракты или таблицы.

## Уточнение прототипа от 25 октября 2026 года

После обсуждения с научным экспертом пользователь потребовал заменить возврат входа без расчёта хотя бы примитивной минимизацией. Решение принято в [ADR-0010](adr/0010-prototype-minimization-solver.md), исходные требования — `REQ-SCI-008`–`REQ-SCI-012`, границы поручения — `REQ-STAGE-004`. Прежние `REQ-SCI-001`, `REQ-SCI-002`, `REQ-SCI-004`, `SCN-STUB-001` и ADR-0002 сохранены как отменённые/заменённые, без повторного использования идентификаторов.

На этом шаге обновляются документы и ссылки существующего application-scaffold без изменения его поведения, критериев и выполненных задач. Новая capability решателя не добавляется в каркас и не синхронизируется в основной каталог спецификаций как реализованная. Перед отдельным предложением OpenSpec о решателе нужно с научным экспертом определить минимальную постановку, раздельные входной/выходной контракты и вычислительную приёмку (`Q-SCI-004`–`Q-SCI-006`, `Q-DOM-002`). Затем подготовить поведение, дизайн и задачи для просмотра пользователем; реализация не разрешается одним обновлением требований.

## Предварительная последовательность последующих областей

| Область | Предмет и необходимые уточнения |
| --- | --- |
| Доменная модель и контракты | Граница снимка версии, единицы и состав, происхождение, права и атомарный конфликт, версии библиотек, раздельные вход задания и результат; OpenAPI и граница адаптера без выдуманного HCh API; согласование с минимальной расчётной постановкой |
| Упрощённый решатель | Согласованные целевая функция, ограничения, метод, данные и область применимости; реальная минимизация, контрольные примеры, диагностика сходимости/ошибок по Q-SCI-004–Q-SCI-006 |
| Сквозной запуск расчёта и CSV | Сохранённые задания, выполнение вне HTTP через упрощённый решатель, маркировка ограничений, точные входы и версии, отдельные вычисленные выходы, обязательный CSV; семантика статусов в необходимом объёме |
| Совместная работа и конфликты | Пользовательские потоки v1/v2, сохранность рабочей копии, создание отдельной модели, предметное сравнение и серверные проверки прав |
| Серии и цепочки | Функции T/P и сетки, предложенные независимость и линейный перенос, расчётные выходные количества поддерживаемых веществ по фазам, баланс и ошибки/несходимость зависимостей |
| Графики и научные библиотеки | Сравнение запусков, графики без вымышленных свойств, общие/личные данные, черновики, публикации и библиотечные привилегии |

Это предварительный порядок, а не разрешение отложить права, версионирование или воспроизводимость в доменной модели. Эти ограничения учитываются с начала проектирования. Контракты и упрощённая модель проектируются согласованно; сквозная приёмка прототипа требует вычисленных выходов, а не копии входа. Исследование HCh/Unitherm и подключение полноценной научной подсистемы планируются отдельно по доступности материалов.

## Проверка документации и трассировка

- Перед правкой проверять существующие документы и пользовательские изменения. Не выполнять commit/push без отдельного разрешения.
- Сохранять стабильные идентификаторы. Для нового требования, сценария, предложения или вопроса вводить новый ID; не менять смысл старого без отражения решения.
- Для требования показывать проверяемые сценарии, для предложения — статус и момент принятия решения, для ADR — основания, последствия и связи. Не приписывать положению обязательность через схему или таблицу.
- При согласовании предложения обновлять его статус и ссылки вместе с соответствующей спецификацией и ADR, сохраняя историю происхождения.
- Проверять относительные ссылки, согласованность статусов, существенные требования, отсутствие секретов, выдуманных команд и неподтверждённых утверждений о научной подсистеме.
- Внешние факты о Unitherm/HCh и инструментах добавлять после проверки с источниками; текущие рекомендации не считать доказанной совместимостью.
