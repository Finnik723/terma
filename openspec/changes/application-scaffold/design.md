# Design

## Context

Мотивация и объём — в [proposal.md](proposal.md). На этапе подготовки существовали только документы, Git-файлы и OpenSpec. После ревью PR №1 пользователь согласовал этот дизайн и разрешил реализацию каркаса, необходимые зависимости и проверки. Актуальное состояние реализации — в tasks и [отчёте проверки](../../../docs/verification.md); это не разрешение на доменную разработку или VPS.

Обязательные исходные границы: один репозиторий и отдельный worker ([ADR-0001](../../../docs/adr/0001-monorepo-and-boundaries.md)), выбранный основной стек ([ADR-0005](../../../docs/adr/0005-selected-stack-and-async-boundary.md)), Windows 10 без обязательных WSL2/Docker, никакого подключения к VPS. [ADR-0008](../../../docs/adr/0008-proposed-tooling-and-environment.md) остаётся предложением. Точные версии и официальные источники собраны в одном месте: [technology-baseline.md](../../../docs/technology-baseline.md).

Решения D-01–D-09 согласованы только для application-scaffold ([ADR-0009](../../../docs/adr/0009-application-scaffold.md)); остальные предложения ADR проекта не приняты автоматически. Поведение изменения задано тремя delta specs. До ревью реализации и последующего архивирования основной каталог спецификаций не обновляется.

## Goals / Non-Goals

**Goals:**

- Получить минимальные независимо проверяемые сборочные и процессные границы.
- Проверять настоящий HTTP между браузером и backend без доменных API и инфраструктуры.
- Дать воспроизводимый путь Windows и Linux CI с точным смыслом каждого результата.
- Сохранить место для будущей научной подсистемы без преждевременного проектирования её типов.

**Non-Goals:**

- Каркас не включает даже научную заглушку: `SCN-STUB-001` остаётся последующей работой.
- Нет постоянного потребителя Kafka, схемы БД, миграций, доменного OpenAPI или подготовки публичного production-развёртывания.
- Docker/Testcontainers не устанавливаются ради каркаса; PostgreSQL не подменяется H2. Перечень прочих исключений задан в proposal.

## Decisions

### D-01. Сборочные границы

Согласованные сборочные границы реализации:

```text
terma/
  pom.xml                         Maven parent/aggregator, backend + worker
  mvnw
  mvnw.cmd
  .mvn/wrapper/maven-wrapper.properties
  backend/
    pom.xml
    src/main/                     Spring Boot MVC + Actuator
    src/test/
  worker/
    pom.xml
    src/main/                     Spring Boot non-web bootstrap
    src/test/
  frontend/
    package.json
    package-lock.json
    .env.example
    src/                          Один технический экран
    tests/                        Компонентные проверки
    e2e/                          HTTP-проверка в Linux CI
  .env.example                    Только локальные JVM-параметры
  .github/workflows/ci.yml
  docs/development.md             Проверенные команды после реализации
  docs/infrastructure-plan.md     Только план отдельного этапа
  docs/                          Существующие источники контекста
  openspec/                      Существующие планирующие артефакты
  .agents/skills/                 Существующая штатная интеграция Codex
```

В корне один Maven reactor с общим parent/BOM Boot; backend и worker выпускают свои executable JAR. Frontend имеет собственные manifest и lockfile, не запускает npm через Maven. Backend не зависит от worker и наоборот; зависимости frontend не попадают в JVM-сборку. Это сборочные модули, не JPMS и не новые микросервисы.

Альтернатива — два независимых Maven-проекта — увеличивает риск расхождения toolchain/BOM. Общий runnable JVM-процесс backend/worker противоречил бы принятой отдельной процессной границе. Корневой JS-workspace и общий Java-модуль пока не нужны.

Будущая точка расширения: worker будет владельцем оркестрации и обращения к отдельной границе адаптера; внутри неё может заменяться ядро вместе с научными данными. Backend не импортирует конкретное ядро. Сейчас это документированное направление зависимости и возможность добавить модуль к aggregator; пустые `Solver`/`Job`-интерфейсы и научные DTO не создаются. Это подготовка к `REQ-SCI-006`, а не выполненный контракт адаптера.

### D-02. Минимальный стек и повторяемость

Используются согласованные версии из [технологической основы](../../../docs/technology-baseline.md). JVM — Java 25 без preview, Spring Boot; compiler target 25. Для обеих сред отдельно согласован Temurin 25.0.4.1+1: у 25.0.5+8 нет Windows-дистрибутива. Maven Wrapper фиксирует дистрибутив и SHA-256; Windows/Unix wrapper-файлы входят в Git. Системный Maven не обязателен.

Frontend — React/TypeScript/Vite, native fetch и простой CSS. Точные direct dependencies, выбранные Node/npm и `package-lock.json` фиксируются в Git; стандартная повторная установка — `npm ci`, не `npm install` с плавающим latest. Не добавлять compiler plugins, UI/router/query/chart-библиотеки для единственного технического экрана. Первичная загрузка зависимостей требует сети, но не сервера пользователя.

Hibernate, JDBC, Liquibase, Kafka, Security, библиотеки визуализации и Testcontainers добавляются по предметной необходимости в последующих изменениях. Hibernate и связанные версии тогда управляются Boot BOM. Альтернатива «установить весь рекомендованный стек сразу» создаёт лишние требования к инфраструктуре без проверяемой функции.

### D-03. Backend и стандартная техническая проверка

Backend запускается как самостоятельный HTTP-процесс на loopback. Используется стандартный Actuator endpoint **`/actuator/health/liveness`**, с явно включёнными probes и минимальным раскрытием деталей. Его контракт — жизнеспособность процесса, не готовность будущей БД/брокера. [Официальное описание Actuator](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html) является основанием; отдельный фиктивный `/api/projects` или демонстрационный доменный endpoint не вводится.

По умолчанию нет persistence/Kafka starters, клиентов и health contributors для отсутствующих интеграций. Успешный liveness при этом корректен только для процесса. UI и документация явно объясняют этот смысл; readiness для научного запуска не существует. Общий health `UP` не используется как доказательство готовности продукта.

Boot API сам по себе не требует PostgreSQL или Kafka. Свободный локальный порт и корректная конфигурация обязательны; bind-ошибка даёт неуспешный запуск. Пока нет аутентификации и защищаемых доменных ресурсов, технический endpoint доступен только в локальном контуре. Публичная публикация этого каркаса не входит в изменение.

### D-04. Worker: bootstrap, а не очередь заданий

Worker — отдельный non-web Spring Boot executable JAR. В первом каркасе реализуется **однократная проверка bootstrap**: загрузить application context, подтвердить успешную инициализацию техническим маркером `WORKER_BOOTSTRAP_OK`, корректно закрыть context и завершиться кодом 0. Ошибка инициализации даёт ненулевой код без маркера успеха.

Тест запускает именно отдельный JVM-процесс собранного JAR с ограничением времени, проверяет код и маркер. Unit/context test отдельно не заменяет этот smoke. Отсутствие HTTP-порта worker и его штатное завершение — ожидаемое поведение каркаса. Постоянный lifecycle, потребление Kafka, выполнение задач и внешняя readiness появятся позднее. В отчёте указывается «bootstrap проверен; обработчик заданий не реализован; инфраструктура не проверена».

Альтернативы: искусственный бесконечный sleep или HTTP-сервер у worker создают видимость полезно работающего исполнителя; поэтому они не нужны для проверки bootstrap. Это ограничение должно быть заметно в документации, а не маскироваться сообщением «worker готов к расчётам».

### D-05. Frontend и реальный HTTP

Один спокойный экран с названием, текстом «Технический каркас; научные расчёты недоступны» и кнопкой проверки связи. Native fetch обращается к liveness backend через ограниченный Vite proxy. Состояния: ещё не проверено, проверяется, backend ответил, backend недоступен/ошибка. Для запроса предлагается таймаут 5 секунд; повторная проверка сбрасывает прежний успех. Проверяются HTTP-код и ожидаемый технический ответ, а не только факт загрузки страницы.

Отдельно постоянно показываются PostgreSQL/Kafka «не подключены / не проверены» и worker «не проверен из браузера». Успешный ответ backend не меняет эти подписи. UI не показывает научные значения, расчёты, CSV или mock-данные домена.

Vite dev и preview слушают loopback с фиксированным портом и `strictPort`; proxy разрешает только нужный технический health-путь. Это устраняет необходимость широкого CORS. Для browser smoke в Linux CI используются собранный frontend через Vite preview с тем же proxy и настоящий executable backend JAR. Preview — техническая среда проверки, не production hosting.

Компонентные тесты Vitest/RTL/jsdom могут подменять fetch для состояний ответа/ошибки/таймаута и обозначаются компонентными. Отдельный Playwright smoke не перехватывает положительный ответ mock-ом: проверяет реальный backend, затем отсутствие положительного результата при остановленном backend. Подменять API ради зелёного HTTP-smoke запрещено.

### D-06. Переменные окружения

Будущие безопасные примеры содержат только реально используемые технические параметры:

| Параметр | Локальный смысл | Проверка |
| --- | --- | --- |
| `SERVER_PORT` | Порт backend, предлагаемое локальное значение 8080 | Неверный формат/занятый порт — ошибка; переопределение проверяется HTTP |
| `SERVER_ADDRESS` | Только loopback, предлагаемое `127.0.0.1` | Нет неожиданного публичного bind |
| `TERMA_BACKEND_URL` | Адрес backend для серверной части Vite proxy, локально `http://127.0.0.1:8080` | Меняет target proxy; не содержит credentials |
| `TERMA_FRONTEND_PORT` | Порт dev/preview, предлагаемое локальное значение 5173 | Число/диапазон проверяются, автоматического выбора другого порта нет |

Это предложения локальных параметров, не параметры или адреса VPS. У worker нет выдуманных Kafka-переменных; non-web режим задаётся штатной конфигурацией Boot в будущей реализации. Для отрицательного bootstrap smoke допустимо заведомо недопустимое значение стандартного параметра Boot, например `SPRING_MAIN_WEB_APPLICATION_TYPE`, чтобы проверить настоящий отказ старта.

[Spring Boot читает окружение процесса](https://docs.spring.io/spring-boot/reference/features/external-config.html); **`.env` не загружается им автоматически**. Будущая Windows-инструкция явно покажет задание env или загрузку безопасного списка, не обещая автоимпорт. В [конфигурации Vite](https://vite.dev/config/) env для proxy/порта загружается явно через `loadEnv` с выбором только нужных `TERMA_*` параметров; передача всего окружения в клиентский bundle не допускается. `TERMA_BACKEND_URL` используется только конфигурацией proxy. [Preview proxy и strictPort](https://vite.dev/config/preview-options.html) настраиваются явно. В примерах нет DB/Kafka URLs, паролей или заглушек адреса сервера. `.env*` с локальными значениями остаются вне Git.

### D-07. Матрица проверок и критерии приёмки

Технические категории оцениваются отдельно. Следующая таблица задаёт согласованную матрицу; фактические результаты, CI и ограничения фиксируются отдельно в отчёте, без подмены ожидаемых результатов выполненными проверками.

| Категория | Windows 10 без WSL2/Docker | Linux CI | Что означает успех | Что не доказано |
| --- | --- | --- | --- | --- |
| Сборка JVM/frontend | Да; выбранные JDK/Node и сеть для первичных загрузок | Да, Ubuntu 24.04; дополнительно Windows Server 2022 runner для wrapper/npm-пути | Два JVM JAR и frontend assets получены, typecheck пройден | Запуск и интеграции |
| JVM unit/context и frontend component tests | Да, без БД/брокера/Docker | Да, обе среды | Проверено только покрытое тестами поведение | Настоящая HTTP-связь, БД, Kafka |
| Bootstrap worker | Да, отдельный JVM; штатный конечный запуск | Да, отдельный процесс с таймаутом | Context поднят/закрыт, код и маркер проверены | Живой consumer, расчёты, БД/брокер |
| Backend process/liveness | Да; локальный HTTP-порт | Да, executable JAR | Процесс реально отвечает на технический запрос | Общая готовность продукта |
| UI/backend HTTP | Вручную в установленном браузере и локальная HTTP-проверка; автоматический Playwright на Windows 10 не обязателен | Playwright Chromium на Ubuntu 24.04, настоящий backend и Vite preview | Получен ожидаемый реальный ответ; при остановке backend UI показывает ошибку | Инфраструктура и научный API |
| Доступность PostgreSQL | Не нужна каркасу; будущая отдельная проверка потребует настоящую БД и защищённый доступ | В каркасе не выполняется | В будущем: проверены соединение/аутентификация к выбранной БД | Проверка приложения и научная корректность |
| Доступность Kafka | Не нужна каркасу; будущая проверка потребует настоящий брокер и достижимые advertised addresses через защищённый канал | В каркасе не выполняется | В будущем: подтверждён broker metadata доступ, не только TCP | Потребление доменных сообщений |
| PostgreSQL/Kafka-интеграции | В будущем могут требовать реальные сервисы; Testcontainers также требует доступный Docker Engine | Отдельное будущее изменение; подходящий Linux runner + реальные контейнеры/сервисы | Настоящая интеграция проверена на целевых технологиях | Не выполняется и не считается зелёной в каркасе |

В CI предлагаются отдельные job/result: Windows build/unit; Linux build/unit; Linux process+HTTP smoke. Имена и результаты явно указывают проверенную категорию. Ни PostgreSQL/Kafka job, ни пустой «integration passed» badge в каркасе не добавляются. Проверка, объявленная обязательной, при отсутствии предпосылок завершается ошибкой, без `continue-on-error` и silent skip. В будущем Testcontainers-профиль не использует H2 и не включается в обычные локальные unit-тесты.

CI не использует пользовательские секреты или VPS. Нужны только загрузки исходников, зависимостей и Playwright Chromium. Официальные GitHub Actions выбираются и закрепляются на проверенные commit SHA при реализации; workflows имеют минимальные permissions и не выполняют deployment. Windows Server runner проверяет Windows-команды, но не подменяет фактическую приёмку локального пути на Windows 10.

### D-08. План PostgreSQL/Kafka на VPS

Фактическое развёртывание **исключено** по решению пользователя. План в будущей `docs/infrastructure-plan.md` содержит следующие шаги для отдельного изменения, без YAML запуска и реальных адресов:

1. Получить только необходимые сведения: версия/архитектура Ubuntu, CPU/RAM/диск, доступная сеть и ограничения. До этого не выбирать размеры, порты доступа, версии образов и параметры хранения по догадке.
2. Выбрать SSH-туннель или VPN; учесть совместный доступ PostgreSQL и Kafka и маршрутизацию metadata/advertised addresses брокера, а не только открытие bootstrap TCP-порта.
3. Спроектировать приватный bind/firewall, аутентификацию, хранение секретов вне Git, TLS при необходимости выбранной схемы, volumes, резервное копирование и восстановление. ДБ и брокер публично не открывать.
4. В отдельном изменении выбрать стабильные PostgreSQL/Kafka и способ установки на проверенной Ubuntu; Docker Engine/Compose — вариант, не установленная инфраструктура и не обязательный Docker Desktop дома.
5. Только после разрешённой настройки выполнить настоящие проверки PostgreSQL connection/auth и Kafka metadata по защищённому каналу; затем отдельно интеграции backend/worker. Не создавать доменные сообщения ради проверки сети.

Неизвестные ресурсы/адреса не блокируют этот каркас. Транспорт не выбирается окончательно заранее: это отложенный вопрос отдельной инфраструктурной работы, а не скрытое условие сборки.

## Risks / Trade-offs

- [Совместимость по документации не равна выполненной сборке] → закрепить версии и проверить полный набор при реализации; значимые изменения вернуть на просмотр.
- [Playwright не поддерживает Windows 10] → browser smoke в Ubuntu CI; локальные обязательные сборки и unit-тесты без Docker, ручной браузерный путь описан отдельно.
- [UP у liveness можно прочитать как готовность системы] → точные подписи UI/документации, отдельные категории проверок и отсутствие общего «всё работает».
- [Worker завершается и может показаться сломанным daemon] → конечный bootstrap — явный контракт первого каркаса; постоянная обработка заданий не обещается.
- [Отложенные persistence/security/Kafka зависимости могут потребовать будущей перестройки] → сохранять модульные границы, не вводить псевдоконтракты и фиктивные интеграции.
- [Неподдерживаемые инструменты IDE или устаревший локальный Node] → CLI-путь независим от платных IDE-функций; обновление toolchain выполняется только на этапе реализации с согласованными версиями.

## Migration Plan

Сейчас миграции и deployment отсутствуют. После просмотра и отдельного разрешения на apply: выполнить [tasks.md](tasks.md), проверить критерии и подготовить PR; не обновлять main напрямую. Откат технического каркаса выполняется обычным обратным Git-изменением через PR, без миграций данных или действий на сервере. Архивировать изменение и перенести delta specs в основной каталог только после реализации, проверок и разрешённого завершения процесса OpenSpec.

## Open Questions

Точные версии, конечный bootstrap worker и Linux-only автоматический browser smoke согласованы пользователем для реализации. Существенные изменения критериев и технологий требуют нового согласования; обычные исправления реализации выполняются в рамках этого дизайна.

Действительно отложены версия/ресурсы Ubuntu, SSH/VPN и конкретная конфигурация PostgreSQL/Kafka (`Q-ENV-001`, `Q-ENV-002` в [реестре](../../../docs/open-questions.md)); их ответы не меняют спецификации каркаса и не требуются для него. Научные/доменные вопросы закрываются в соответствующих последующих изменениях.
